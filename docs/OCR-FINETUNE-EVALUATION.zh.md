# 终端与 BIOS OCR 垂直微调评估

[English](OCR-FINETUNE-EVALUATION.md) | 简体中文

日期：2026-09-18。本文是后续技术评估，尚未进行训练，不是使用现有工具的前提。产品使用通用 ocrs 模型；暂停的 BIOS 颜色/布局规则原型已移出产品代码。

公开数据来源、许可筛选与第一轮配方见 [OCR 数据来源筛选](OCR-DATA-SOURCES.zh.md)。

## 结论

值得做一次小模型领域微调试验。场景有固定/有限字体、低分辨率、较少旋转与透视变化，且可合成大量带精确标签的文本；现有错误包含低对比度选中行、括号、数字与字母混淆。预计可以改善，但收益和跨固件泛化必须通过独立真实图片验证。

优先微调现有 ocrs 检测/识别模型，保留 Rust + RTen 部署。训练在 Python/PyTorch/CUDA 环境完成，导出 ONNX 并做 Rust 推理一致性检查；用户端不需要训练环境。保持原架构的导出集成风险最小，换架构需先验证 RTen 算子及输入输出兼容性。

## 三种监督目标

1. 文字识别：文字行/片段图片对应逐字准确的字符串，重点覆盖数字、大小写、空格、括号、下划线、命令与路径。首先修正看到了文字却读错字符的问题。
2. 文字检测：全屏图对应文字框/多边形，训练低对比度、高亮反色和小字，减少漏行。
3. 交互状态：全屏/带上下文的 RGB 区域对应选中、未选中、禁用、光标、弹窗及标签值关系。它需要额外标签和模型输出，不能靠只训练文本转录目标自动获得。现有 ocrs 识别输入为灰度行图；状态分支应保留颜色和上下文。复杂操作规划继续由外部 Agent 完成。

第一轮可先完成前两项，再根据外部视觉模型的实际需求决定是否训练状态分支。初始目标以英文/ASCII 及符号为主；中文、框线字符等扩展字符集要另行准备数据并调整输出层。

## 现有数据

本地截图集（现已移至仓库外的运维目录）中有 161 张 PNG，按 RGB 像素 SHA-256 去重后为 74 张：

- 800×600：139 张，58 张像素唯一图，主要为同一 Aptio BIOS 的页面及选中状态。
- 1024×768：16 张，12 张像素唯一图。
- 720×400：6 张，4 张像素唯一图。

像素不同也不一定是独立样本，光标、时钟、选中项变化可能造成差异。不同主机的相同菜单不能仅按主机拆分训练集与测试集。现有数据适合错误分析、标注流程和窄场景验证；广泛的终端与 BIOS 产品需要更多字体、界面模板、分辨率和状态。开发中反复查看过的图片也不能当作从未接触的最终验收集。

## 数据预算（项目估算，不是成功保证）

| 任务 | 首轮真实标注预算 | 合成补充建议 |
| --- | --- | --- |
| 行文字识别微调 | 5,000–20,000 个真实文字行/片段 | 50,000–200,000 个合成文字行 |
| 检测微调 | 500–1,500 张带文字框的全屏图 | 按真实界面分布合成全屏样例，先验证合成与真实差距 |
| 状态/布局分支 | 1,000–3,000 张带状态/关系标注的截图 | 各主题、选中项、弹窗组合与困难负例 |

上述素材可以复用：一张全屏图可以同时提供检测框、多个识别片段及状态标签。识别数据量按文字行计算，不能把 5,000 行写成 5,000 张全屏，也不能把同一图的数据增强变体算成独立真实样本。

识别合成覆盖真实的终端/BIOS 字体、字号、颜色、反色、间距、压缩失真及截断。内容应包含随机数字/IP/端口、路径、命令和参数组合，避免只记住固定 BIOS 菜单词汇。合成器的绘制规则用于生成训练数据，推理不需要依赖固定坐标或颜色阈值。终端样本尽量由受控程序或虚拟终端渲染，并保留生成文本和布局作为标签。

AI/OCR 可预标注，人工或严格复核流程纠错；模型生成的文字不可直接充当真值。训练、验证和测试按模板/菜单家族、字体、内容及采集会话分组；所有同源裁片与增强变体留在同一分组。单独保留未参与调参的真实新截图。混入适量通用数据，监控原场景退化。

## 硬件与时间预算

- 优先：单张 NVIDIA CUDA GPU，24 GB 显存，主机 32–64 GB 内存及约 100 GB 可用 SSD，足以作为这一轮小型 OCR 实验的配置目标。上游 ocrs 的原始训练使用 A10G 24 GB。
- 起步：8–12 GB 显存可尝试行识别微调，减小 batch、按行宽分桶；全屏检测受输入尺寸影响更大，需实测显存。此档是工程估算，未在项目中验证。
- 多卡/A100/H100 暂无必要。当前 Xeon 主机适合数据渲染、标注服务和 CPU 推理；纯 CPU 训练用于小批调试即可。
- 单轮小模型微调先按数小时到一天的 GPU 时间预留，数据整理与标注通常更费工程时间。这不是测速结果：先跑数百至一千步，记录显存、吞吐、验证收敛趋势，再估算完整实验。
- 训练 GPU 与交付依赖分开；保持现有架构时仍可在 Rust CPU 端推理。量化及换架构必须重新检查数字、符号和长行准确性。

## 建议实验路径

1. 建立按场景分层的真值集，拆开检测漏行与字符误识别；记录通用 ocrs 及一个成熟 OCR 对照引擎的结果。
2. 用现有真实图制作 500–2,000 行的早期调试集，配合合成数据验证训练、导出、Rust 推理全链路。它只用于验证流程和窄场景收益，不承担通用验收。
3. 补齐首轮真实行数据及合成数据，固定检测器微调识别模型；比较真实样本、真实加合成、以及是否加入通用数据三种训练组合。
4. 对仍漏检的高亮行、小字进行检测器微调；用独立真实集检查端到端结果。
5. 需要本地结构化交互状态时，再训练 RGB 状态/关系模型。OCR 与状态模型的错误应分别可观察。
6. 评估字符错误率、整行完全正确率、IP/命令/配置值完全正确率、漏检率、状态/配对准确率及 CPU 延迟；以关键字段错误显著下降且原场景不退化作为去留依据，不承诺训练后无误。

保留固定独立测试集，不能把反复查看错误后补进训练的样例继续计入未见测试。截图中已经丢失的内容不能通过训练恢复为可靠的原始 shell 字节输出。
